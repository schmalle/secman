- **Public standard download: any standard, any release, over a plain GET** — the unauthenticated `/requirements/download` page could export the whole corpus or one use case, but not a *standard*, and there was no way to ask for "the latest released version of the IT/OT Security standard" from a script. `GET /api/requirements/export/{docx,xlsx}` now take four optional query parameters — `standard` (exact name, case-insensitive), `standardId` (wins if both given), `release` (`latest`, or an exact version) and the pre-existing `releaseId` — all `IS_ANONYMOUS`, matching the four public export endpoints that already existed. A standard has **no direct link to requirements**: `Standard.useCases` joins `Requirement.usecases`, so a standard selects every requirement tagged with any of its use cases, de-duplicated and ordered by chapter — the same rule `StandardController.getStandardRequirements` applies. Release-scoped standard exports filter `RequirementSnapshot.usecaseIdsSnapshot` through `ReleaseRequirementScopeService`, so a historical download is reproducible rather than re-derived from live rows. Three failure modes fail loudly rather than degrading: `release=latest` with **no ACTIVE release** is a 404 and never silently serves the live corpus ("the latest release" and "whatever is in the editor" are different answers); `releaseId` and `release` identifying different releases is a 400 rather than one silently winning; and a standard with **no use cases mapped** returns `{"message": "No requirements found for this standard"}` rather than falling through to everything, so a half-configured standard cannot publish the full corpus by accident. Name matching is a bound-parameter `LOWER(s.name) = LOWER(:name)` fetch-join (`Standard.useCases` is LAZY, so a detached read would throw); an over-long name is rejected before the query runs. The standard name reaches `Content-Disposition`, so `StandardExportScopeService.exportFilename` strips it to `[A-Za-z0-9._-]`, collapses repeated dots and drops a leading one — `IT/OT Security` becomes `ITOT_Security`, `../../etc/passwd` becomes `etcpasswd` — and the xlsx endpoint gained the `"`/CR/LF strip the docx path already had. A new slim `GET /api/standards/public` returns `{id, name}` only so the picker works logged out; `GET /api/standards` stays `IS_AUTHENTICATED`, keeping descriptions, use-case mappings and timestamps behind auth. - **EOL matching for applications and frameworks: Java's nine distributions, the .NET family, and four rules that stop the estate being told supported software is dead** — the EOL dashboard showed operating systems only while `/products` plainly listed `.Net Framework 4.8` and `.NET Core 1.0`–`6.0`. The cause was not a missing data source: `EolSubjectType.ASSET_PRODUCT` and `scanInstalledProducts` already existed and were correct. `installed_product` was simply **empty at scan time** — it is fed by CrowdStrike **Discover** via the separate `secman installed-products` CLI, not by the Spotlight vulnerability import that fills `vulnerability.vulnerable_product_versions` behind `/products`. The first-ever Discover import landed 182,131 rows across 2,010 assets and the scan went from 304 findings to real coverage; **no new scan source was needed and none was added.** What *was* broken is matching, in four ways, each proven against the live inventory rather than inferred. **Java could not match at all**: endoflife.date publishes no generic `java` product — it publishes `oracle-jdk`, `amazon-corretto`, `eclipse-temurin`, `azul-zulu`, `microsoft-build-of-openjdk`, `redhat-build-of-openjdk`, `openjdk-builds-from-oracle`, `graalvm-ce` and `oracle-graalvm`, because Oracle JDK 8, Corretto 8 and Temurin 8 end on different dates — so the five curated aliases targeting `"java"` resolved to a key no product owned and were **dropped silently at index build time**, which is the documented behaviour for speculative targets and is exactly why the failure was invisible. Each spelling now maps to the distribution that ships it, an unidentifiable build produces no finding rather than borrowing another vendor's date, and where the name is ambiguous (`OpenJDK Platform 11`) the vendor decides — enabled by adding corporate suffixes (`Inc`, `Corporation`, `Ltd`, `GmbH`, `LLC`) to the noise tokens so `Oracle Corporation OpenJDK Platform` tokenizes to a usable alias prefix. **Legacy Java versions were unmatchable**: Java numbered releases `1.x` up to Java 8 and plainly `x` after, so `1.8.0.392` segments to `[1,8,0,392]` and prefix-matches no cycle; it is now rewritten to `8.0.392`, only for the Java distributions and only when the leading segment is exactly `1` (`1.4` → `4`, which no cycle carries, so it fails closed). **Labelled cycles matched by list order**: every `windows` cycle upstream carries an edition label (`10-1507`, `11-24h2-e-lts`) and cycle comparison keeps only the leading numeric run, so `10-1507` collapsed to `[10]` and the Windows Server 2022 build `10.0.20348.3451` prefix-matched it — **3,672 findings, 42 % of the total, reporting supported servers as end of life since 2017**, decided by nothing but release ordering. Labelled cycles are now skipped (`isNumericCycle`), because which edition a bare build number belongs to cannot be recovered without a build-to-release table the catalogue does not publish; Windows Server is unaffected, its cycles are plain numbers. **Distribution packages were judged against upstream lifecycles**: a packaging revision (`1.18.0-6ubuntu14.4`, `2026c-1.el8_10`, `3.4.1-11.amzn2`, `~esm1`) *proves* the support contract belongs to the distribution — Canonical still supports nginx 1.18 long after upstream dropped it — and a maintainer vendor (`Ubuntu Developers <ubuntu-devel-discuss@…>`) proves it even when the version looks plain, which is how the Ubuntu npm library `node-arrify 2.0.1-2` was reported as "Node.js 2, end of life". Both are rejected; Red Hat and Amazon Linux are deliberately **not** vendor-blocked because their packages carry `.el8`/`.amzn2` in the version and blocking the vendor would make `redhat-build-of-openjdk` unmatchable. Also curated: `Microsoft Windows Desktop Runtime - 8.0.21` is the .NET desktop runtime, and without an explicit entry the shorter `microsoft windows` alias captured it and reported **.NET 8 as Windows 8, EOL 2016**; and `ASP .Net Core` → `dotnet` (no product of its own upstream, its versions track .NET exactly), noting the alias is `asp net core` because tokenization strips the leading dot. Net effect on the live estate: 304 → **4,492 findings** (3,386 EOL, 1,106 approaching) with the Windows, Node-library and distro-package false-positive classes eliminated — Internet Explorer 11 (762), .NET 8 approaching (443), SQL Server 2016 (279), .NET 6 (165), Visual Studio 15.0/16.0/10.0, Splunk 8.1/9.0/9.2, and Oracle JDK 6/7/8/11 plus Corretto and Oracle's OpenJDK builds now reporting for the first time. Unrelated fix required to verify anything at all: `RequirementExportTemplateValidationServiceTest` referenced `org.apache.poi.xwpf.usermodel.HeaderFooterType`, which does not exist (it is `org.apache.poi.wp.usermodel`), and that single unresolved reference had been failing `compileTestKotlin` and therefore blocking the **entire** backend test suite since the requirement-export-template commit. - **AWS account onboarding: welcome mail, direct and guided risk assessments** — the "new AWS account discovered → mail the owner and start an assessment" path becomes a three-mode capability, and the scoping decision moves to the person who actually knows. `WELCOME_ONLY` sends a welcome mail from a classpath template; `DIRECT` additionally starts an assessment for a use case the operator names (today's behaviour); `GUIDED` mails the owner a **one-time, expiring link** whose answers resolve through admin-configured rules into a *set* of use cases, and creates the assessment only on submit, scoped to the **union** of every matching rule. All three run from CLI (`--onboarding-mode`, `--welcome-email`, `--questionnaire-expiry-days` on `import` and `import-s3`), REST and MCP, all dry-runnable, plus a first-class `simulate-onboarding` verb (CLI + REST + MCP `simulate_account_onboarding`) that runs the whole path against a made-up account id and address — the *same* code path a real import runs, not a mock, which is what makes it a rehearsal and why it is rate limited, audited, and stamps every simulated mail with "this is a test, sent by <actor>". **The backward-compatibility contract is the load-bearing part**: a caller sending only `startRiskAssessment=true` — every `extensions/` client, `import-s3`, both existing E2E drivers — resolves to `DIRECT` **with no welcome mail**, byte-identical to before, reconciled in one function (`AccountOnboardingMode.resolve`); an explicit non-`DIRECT` mode combined with that flag is rejected, never guessed. **The matcher never decides**: it sees only choice ids (a BOOLEAN question is two choices, no second code path), every matching active rule contributes and nothing wins, `priorityOrder` is display order only, the single `isDefault` rule is consulted **after** everything else fails, and a resolution producing no requirements in the ACTIVE release is an error rather than an empty questionnaire. Answers that match nothing are **persisted** and the invite stays usable, so an admin can add the missing rule and the owner's original link still works. Rules are normalized tables, not a `ruleJson` blob (`DemandClassificationRule`'s precedent exists for a recursive condition; this one is a flat AND over choice ids, and the rule→use-case link needs real FK integrity). **The public questionnaire is the first genuinely unauthenticated write path in the codebase** and is treated as such: 256-bit `SecureRandom` token (not `UUID.randomUUID()`, because this token *creates* an assessment), single use enforced by a guarded UPDATE **claimed before** creation, 14-day expiry, a byte-identical 404 for malformed/unknown/expired/used/cancelled so the endpoint is no enumeration oracle, the account id **masked** to four digits and the owner email never returned, a new bounded fixed-window rate limiter with a dedicated failed-lookup bucket, `@Secured(IS_ANONYMOUS)` explicit on every method plus an `intercept-url-map` entry so a stale `secman_auth` cookie cannot 401 an owner out of their own link, and the full token never logged, never returned by any API, never printed by the CLI, never in an MCP result and never minted by a dry run — all asserted. Unanswered invites get one reminder then lapse; **nothing is ever auto-created**, because an assessment scoped by a guess looks authoritative and is not. `createAssessment` now takes `useCases: Set<UseCase>` (`use_case_name` widened 255→1024 in V253) and `sendStartNotification` was promoted to `notifyAssessmentStarted` so the guided path reuses the identical mail. Five private helpers were extracted from `AwsAccountRiskAssessmentService` into `EmailTemplateRenderer` — with a **closed template allowlist**, because the basenames are operator config and interpolating one into `getResourceAsStream` would be a classpath-traversal read — and the twice-copied recipient regex into `EmailAddressValidator`. New: ADMIN-**or-SECCHAMPION** admin API and UI (a deliberate widening vs Demand Classification's read-both/write-ADMIN, with a coverage matrix that shows which answer combinations would dead-end *before* an owner hits one), `/onboarding/[token]` public page, `docs/ACCOUNT_ONBOARDING.md` with 28 worked examples covering every mode × dry-run × surface, and the `/account-onboarding` skill in both trees. **OWASP: A01/A02/A03/A04/A05/A07/A08/A09 touched — 0 BLOCK.** **The Kotlin and CLI halves are compile-unverified**: the session had Java 21 only, no Gradle 9.7.0 distribution (services.gradle.org 403s through the agent proxy) and no Maven Central route. - **End-of-life lifecycle management: a catalogue, a matcher that refuses to guess, owner mail and a top-10 repository ranking** — secman gains a full EOL feature: `secman eol-sync` pulls a lifecycle catalogue and re-matches every system's OS and installed products plus every imported GitHub repository's dependencies against it; `secman send-eol-notifications` mails account owners about software going EOL in the next 12 months; `/vulnerabilities/eol` answers "which software in my account / on my servers is end of life"; and ADMIN/SECCHAMPION get the top 10 repositories by distinct EOL components. **Source: endoflife.date** — public, unauthenticated, ~350 products covering both halves of this inventory (Windows/Windows Server, RHEL, Ubuntu, Debian, SLES, Amazon Linux, ESXi, Java, .NET, Python, Node.js, nginx, Apache, Tomcat, PostgreSQL, MySQL/MariaDB, Spring Boot, Kubernetes). Microsoft's Lifecycle API was considered and rejected *as a replacement* (Microsoft-only, needs an Entra app) but is a sensible future second `sourceKey` — `EolProduct` is keyed `(source_key, product_key)` for exactly that. **The fetch runs in the backend, not the CLI**, same shape as `import-github-repos`: the host allowlist, the SSRF checks and the audit record stay in one place and the CLI host needs no egress. **The matcher never guesses** — a component whose version cannot be parsed, or whose version matches no cycle, produces no finding, because a false "end of life" on a production server lands on an owner's remediation list and costs more than a miss. Two consequences it took real care to get right: a version embedded in the name beats the version field (Windows Server reports build `10.0.17763`, which matches no cycle; the `2019` in the name does), and a cycle upstream flags EOL *without a date* is EOL with a **null** horizon, never a zero-day countdown — the owner mail promises "within N months" and must not put undated cycles in that window. Cycle resolution compares whole dot-segments, so `4.10` never matches cycle `4.1`. **Repository components are a deliberate under-approximation**: a Dependabot alert names the vulnerable *range*, never the resolved version, so the scan takes the range's upper bound — from `< 4.17.21` it knows the dependency is below 4.17.21, hence if the cycle containing 4.17.21 is already EOL then whatever is installed is in that cycle or older and is EOL too. Only `EOL` is recorded there ("approaching" says nothing about the older version in use) and an unparseable range is skipped. Findings are **replace-per-run** by `scan_run_id` with an explicit delete — `Asset` owns no cascade to `EolFinding`, because mixing cascade with manual delete-insert is what dropped 166,812 rows to 1,819 in the CrowdStrike import. Only EOL and approaching-EOL rows are stored; persisting supported ones would be a row per product per asset. **Every asset-scoped read resolves accessible asset ids first and binds them as an `IN` list**; `EolFindingRepository` has no unscoped find-all on a user-facing path, the repository ranking is ADMIN/SECCHAMPION only mirroring `GithubRepositoryController`, and an out-of-scope asset id answers 404 identically to a nonexistent one. Recipient resolution reuses `AwsAccountRecipientResolver` rather than inventing an ownership model, and addresses are rejected rather than repaired (the value is an SMTP recipient, a stored result and a log line — three sinks from one string). New: `src/backendng/…/domain/Eol*`, `EolCatalogClient/CatalogSyncService/VersionMatcher/ScanService/QueryService/NotificationService/AdminService/Writer`, `EolController`, CLI `eol-sync` + `send-eol-notifications`, `/vulnerabilities/eol`, a Lifecycle badge on `/installed-products`, `docs/EOL.md`, and the `/e2eeol` skill. **OWASP: A01/A03/A04/A05/A08/A09/A10 touched — 0 BLOCK, 35 REVIEW, all reviewed** (26 A01-sql-authz on catalogue reference-data reads and on scoped reads that take a bound `assetIds` list; 6 A03-shell-sh on quoted `curl` argv in the E2E driver; 1 A04-todo-auth on the controller's `IS_AUTHENTICATED` default, deliberate because the reads are asset-scoped and the admin verbs carry their own `@Secured`; 1 A10-outbound inside the test that asserts the SSRF guard). **Kotlin is compile-unverified** — no Gradle distribution and no Maven Central route in that session; the frontend `npm ci && npm run build` gate and the 99-test frontend unit tier are green, as is `check-skill-sync.sh`.

- **Zero-trust mobile relay: a DMZ server, secman's RBAC mirrored onto it, and an iOS app** — secman gains an outbound-only publisher (`SECMAN_RELAY_ENABLED=true`, off by default) that pushes an admin-level status snapshot to a standalone Go relay in a DMZ; the relay serves it read-only to iPhone/iPad clients and **can never reach back**. Direction is the whole design: secman dials out, the relay holds no secman credential and is never told where secman is, so a fully compromised DMZ box discloses dashboard aggregates and nothing else — no database, no write path, no lateral move. That is why a reverse proxy was rejected: a proxy needs an inbound path *and* a credential inside the DMZ. **Authorization is secman's, mirrored, not reinvented**: every snapshot section carries the roles its originating controller demands (`DashboardController`'s `@Secured("ADMIN","SECCHAMPION")` → `requiredRoles` on `kpis`), secman pushes each user's live roles as a principal record, and a read needs a matching role **and** a device scope naming the section — a scope narrows, never widens. Roles are resolved from the principal on every request and never cached on the device or baked into a token, so a demotion bites on the very next request with nothing to invalidate; principals are replace-on-push so roles can shrink, revocations stay additive so one is never undone by omission, and out-of-role / out-of-scope / nonexistent all answer an identical 403. **Sign-in layers three separate proofs**: Apple and Google ID tokens verified against their JWKS (RS256 pinned, iss/aud/exp and a single-use relay-issued nonce all checked — `aud` is what stops a token minted for another app); GitHub via the relay as a confidential OAuth client so the app never holds a GitHub credential; and a Secure Enclave P-256 key proving the device on every request. Verifying an identity grants nothing on its own — only the principal list secman pushed does. **Admins are held to a stronger bar**: a privileged role can only be bound via Apple or Google, re-checked on *every* token issue so a promotion invalidates a weakly-bound device, and the relay refuses to boot if a privileged role has no reachable strong provider. Binding is proof-of-possession throughout: the login nonce is bound to the device key and the binding request must carry that key's signature, so a captured ID token cannot register someone else's key. TLS on a selectable port in three modes — a **stdlib RFC 8555 ACME client** (Let's Encrypt, HTTP-01, renewal at 30 days), a file pair hot-reloaded on change, or plaintext for ALB termination behind an explicit `RELAY_PLAINTEXT_ACK=true`. The relay is **zero-third-party-dependency by contract** (its supply chain is the Go release plus this repo, and `go build` needs no module proxy), snapshot state is memory-only, and it fails closed on weak or placeholder secrets exactly as `JwtSigningValidator` does. 189 Go tests including a mock ACME CA that signs a real CSR and verifies every JWS, a mock OIDC issuer covering algorithm confusion / audience / issuer / expiry / nonce replay / key rotation, and end-to-end RBAC, revocation and staleness cases; a shared known-answer vector pins the ingest signature across Kotlin and Go so the two cannot drift silently. New: `src/relay/`, `com.secman.relay`, `RelayIdentity` entity, ADMIN-only `/api/relay/*`, `docs/RELAY.md`, and `extensions/secman_app_ios` (SwiftUI, iOS 26+, no third-party packages). **OWASP: A01/A02/A03/A04/A05/A07/A09/A10 touched — two A02 BLOCKs remain by design** (`RelayDigest` — SHA-256 as a message digest and over a 100-bit single-use token; BCrypt is the wrong tool there and would turn an O(1) lookup into an O(n) scan of a slow function on an unauthenticated endpoint), A10 reviewed: the outbound URL is operator config no request can influence. **The Kotlin and Swift halves are compile-unverified** — Maven Central was blocked by the egress policy, only JDK 21 was present, and there is no Swift toolchain.

- **Generic chat notifications (Slack + Telegram), configurable per user** — SecMan can now message a user in Slack and/or Telegram when a reportable event completes, with each user choosing their own destination and, independently per channel, which events they want. Two events ship: `CROWDSTRIKE_REPORT_COMPLETED` ("New CrowdStrike report completed") and `AWS_ACCOUNT_IMPORT_COMPLETED` ("New AWS account import completed"). **Architecture is transport- and event-agnostic on purpose.** Publishers know nothing about chat: they publish a `ChatNotificationEvent` (event type, title, summary, label/value fields) and `ChatNotificationEventListener` (`@EventListener @Async`) hands it to `ChatNotificationService`, which resolves subscribers, destinations and rendering. Adding a reportable event is a `NotificationEventType` constant plus one publish call — the settings APIs, both settings UIs and the dispatcher all derive from the enum, so nothing else changes. Adding a transport is one client plus one branch, with no publisher touched. **Subscriptions are rows, not columns**: `user_notification_subscription (user_id, channel, event_type)` — so a new event type or a whole new channel costs no migration, "who wants X over Slack" is a single indexed lookup on the dispatch path, and one user can route CrowdStrike to Slack and AWS imports to Telegram. Saving one channel's settings never disturbs the other's subscriptions (the replace is a per-channel diff, which also preserves `created_at` on kept rows). **Destination resolution.** Slack: personal incoming webhook → the user's channel via the workspace bot → the workspace default channel. Telegram: the user's chat ID is always required (Telegram addresses a conversation, not a person), with the token being the user's personal bot if set, otherwise the workspace bot — so a personal bot keeps working even when workspace delivery is switched off. A subscriber who is enabled but has nowhere to send is recorded as `SKIPPED`, not `FAILED`; the UI resolves the same precedence client-side (`resolveSlackDestination` / `resolveTelegramDestination`) and warns *before* save rather than letting someone tick boxes that silently deliver nothing. **Where the events fire.** AWS account imports complete in one call, so `UserMappingBulkImportService.execute` (REST bulk + MCP, tagged with the calling entry point) and both `ImportController` upload paths publish immediately, after the import has committed and last among the post-commit side effects. CrowdStrike has no such point: a full CLI import arrives as ~94 sub-batch requests across 3 concurrent workers with no well-defined last batch, so `ImportCompletionNotifier` accumulates the run's totals in memory and a `@Scheduled` sweep publishes exactly **one** event once `SECMAN_CHAT_CROWDSTRIKE_QUIET_PERIOD_SECONDS` (180s) have passed with no activity — the same server-side debounce shape, and for the same reason, as `MaterializedViewRefreshService.requestDeferredRefresh`, and it keeps working for older CLI versions, the `/api/crowdstrike/vulnerabilities/save` path and manual callers. **Security.** The per-user Slack webhook URL is the only place in the platform where a non-admin supplies a URL the backend then fetches, so it is checked against a fixed `https://hooks.slack.com/` prefix *and* parsed-host equality (a prefix match alone passes `https://hooks.slack.com.evil.example/...`), rejects userinfo, non-default ports and non-https, and redirects are never followed. The Telegram bot token is interpolated into the request URL **path** (`/bot<token>/sendMessage`), so its `<digits>:<secret>` shape is validated as a security control — a token containing `/` or `..` would otherwise redirect the request to another path on the API host. Slack channels and Telegram chat IDs are validated against conservative character classes. Every credential (both workspace bot tokens, each user's webhook URL and personal bot token) is stored through `EncryptedStringConverter`, never returned by any API — the responses report only `…Configured: true/false` — and the `***HIDDEN***` mask is accepted back to mean "keep the stored value", with `''` meaning "clear it". Slack messages escape Slack's three reserved characters so an imported hostname cannot inject a fake link; Telegram messages are sent with **no** `parse_mode`, deliberately, because MarkdownV2 reserves 18 characters and rejects the whole message on one unescaped occurrence. Every route acts on the caller's own settings — the user id comes from the token and is never read from the body. Dispatch is deliberately **not** `@Transactional`: it performs outbound HTTP with a multi-second timeout per recipient, and wrapping it would pin a pooled DB connection for the whole fan-out (the 2026-07-21 HikariCP starvation incident was exactly that shape).
