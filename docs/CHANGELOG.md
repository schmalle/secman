# Changelog (archived from CLAUDE.md)

The full history. Every change is written here **verbatim** when it happens; CLAUDE.md's `## Recent Changes` carries a 2–3 line summary of the three newest and nothing more. Nothing is ever summarized on the way in — this file is the greppable detail. Newest first.

- **Profile picture management (upload / crop / replace / remove)** — any authenticated user can now set an avatar from `/profile`; it replaces the generic `bi-person-circle` icon beside their name in the header dropdown. Scope is deliberately **own picture only** — there are no ADMIN-manages-others endpoints, and none of the three routes (`GET`/`POST`/`DELETE /api/users/profile/picture`, all on the existing `UserProfileController`) takes a user identifier, so the subject is always `authentication.name` and cross-user access is *structurally* impossible rather than merely checked. The paths are two literal segments, so they cannot collide with the ADMIN-gated single-segment `@Get("/{id}")` on `UserController`, which shares the `/api/users` prefix. **Bytes are stored in the database but never as uploaded**: `ProfilePictureService` validates cheapest-first (size cap → MIME allowlist → filename-extension/MIME agreement → magic bytes → header-only dimensions → the `ImageReader`'s own `formatName`) and then decodes, centre-crops to a square, scales to 256 px and re-encodes. That round trip — not the magic-byte sniff — is the control that actually matters: it destroys polyglot payloads (a valid PNG with `<script>` appended still decodes as a PNG and would pass any header check) and strips EXIF/GPS metadata, verified by a dedicated test. The **dimension probe runs before `reader.read(0)`**, so a 2 MB PNG cannot decode into a multi-gigabyte `BufferedImage` and trip `-XX:+ExitOnOutOfMemoryError` on the 1 GB heap; without that guard the endpoint would be a single-request kill switch. WEBP is deliberately **absent** from the allowlist (the JDK has no WEBP reader, so accepting it would mean storing bytes that were never decoded) — this costs nothing in practice because the frontend cropper exports its canvas as PNG, so WEBP/HEIC sources still work end to end. SVG is rejected three independent ways: not in the allowlist, `.svg` already in `SecurityService.DANGEROUS_EXTENSIONS`, and no SVG `ImageReader` exists. Only the JDK is used (`javax.imageio`/`java.awt.image`); `-Djava.awt.headless=true` was pinned in `applicationDefaultJvmArgs`. Storage is a **side table** `user_profile_picture` (V249, 1:1, `ON DELETE CASCADE`), not a column on `users`: `users` is loaded on every authenticated request and **`@Basic(fetch = LAZY)` on a `@Lob` is inert without Hibernate bytecode enhancement, which this build does not enable** — a blob column on `users` would therefore be fetched eagerly, every time. For the same reason the hot metadata paths use the blob-free projection `findUpdatedAtByUserId`, never `findByUserId`. `UserProfileDto` and `AuthController.StatusResponse` gained `hasProfilePicture` + `profilePictureUpdatedAt` (both defaulted, so purely additive); `LoginResponse` and the four `sessionStorage['user']` writers were deliberately **left alone** — `auth-init.ts` and `login/success.astro` store the whole `/api/auth/status` response verbatim and `Login.tsx` redirects immediately into a fresh status call, so they pick the fields up for free. **The header `<img>` is gated on `hasProfilePicture` rather than rendered unconditionally with an `onError` fallback**: `tests/js-error-scanner.mjs` records any status ≥ 400 as a failure, so an unconditional request would 404 on every page for every user without a picture and fail the `/e2ejs` merge gate. For the same reason `DELETE` returns 204 unconditionally instead of 404 when nothing is set. Frontend: new `ProfilePictureCard.tsx` (preview, drag & drop, and a hand-rolled canvas crop/zoom step — pointer-drag to pan, wheel/slider to zoom, exported at 512 px via `canvas.toBlob`; no cropping library added, the repo carries none), mounted as the first card on `/profile` and seeded from the profile fetch that already ran, so no extra metadata request. After a save or removal it patches `window.currentUser`/`sessionStorage` and re-dispatches the **existing** `userLoaded` event that `Header.tsx` already listens for, so the navbar avatar updates without a reload. Serving uses `inline` disposition — the first such endpoint in the repo — which is safe only because the `Content-Type` served is the stored, service-chosen value and never the client's declared one, and the `Content-Disposition` filename is synthesized from a `Long` and a constant so no user input reaches a response header. Upload, removal **and rejection** are audit-logged (a stream of `PROFILE_PICTURE_UPLOAD_REJECTED` is exactly the signal wanted when someone probes with polyglots). Tests: `ProfilePictureServiceTest` (19 cases incl. the polyglot-stripping and bomb-guard proofs), `UserProfilePictureIntegrationTest` (happy path, replace-updates-one-row, every rejection branch, 401 on all three routes, idempotent delete, cross-user isolation, cascade). Docs: `docs/ENVIRONMENT.md` (`SECMAN_PROFILE_PICTURE_*`).

- **MCP `get_vulnerabilities` no longer reads the whole vulnerability table** *(pre-existing OOM fix, unrelated to the EDR KPI change it shipped alongside)* — the no-filter branch for delegated (non-ADMIN) callers built its page by calling `vulnerabilityRepository.findAll()` and filtering/slicing in Kotlin, so every request loaded ~1.1M entities into heap and exhausted the 1 GB dev heap with an `OutOfMemoryError`; the cost scaled with the table rather than the requested page size.   Boxes that legitimately cannot run an agent are handled by a **third, orthogonal exception axis** `kind: ExceptionKind { VULNERABILITY, NO_EDR }` (V247) on both `VulnerabilityException` and `VulnerabilityExceptionRequest` — a *new enum*, not a new `Subject`/`Scope` value, so none of the ~15 exhaustive `when(subject)`/`when(scope)` blocks break and suppression semantics are not inherited. A NO_EDR exception is `scope=ASSET` only, stored with the filler `subject=ALL_VULNS`, **suppresses nothing**, and merely leaves the KPI denominator (reported separately as `excludedByNoEdrException` in the card subtitle). It reuses the entire request → approve/reject/cancel workflow, audit log, SSE badge and expiry scheduler. The "suppresses nothing" invariant is enforced in all three synchronized predicates — `VulnerabilityException.matches()`, `ExceptionMatchSql.EXCEPTION_MATCH` (one leading conjunct, compile-time interpolated into every native site incl. the `recomputeExcepted*` UPDATEs) and `ExceptionMatchIndex` — plus a defence-in-depth filter in `VulnerabilityService.getActiveExceptions()`. **The SQL guard is `(e.kind IS NULL OR e.kind = 'VULNERABILITY')`, not plain equality**: V247 adds the column `NOT NULL DEFAULT` with an explicit backfill, but if a NULL ever occurred (Hibernate `hbm2ddl.auto` creating it where V247 didn't apply, a restored pre-V247 dump) plain equality would stop *every* legacy exception matching and the 03:00 `recomputeAllExceptedScheduled` would clear `excepted` fleet-wide, unattended. The KPI queries use the opposite convention — plain `kind = 'NO_EDR'` — because tolerating NULL there would silently read every legacy exception as an EDR exemption. V247 also **rebuilds `idx_vuln_exception_covering` with `kind` leading**, since V203 created it specifically to keep the correlated `EXCEPTION_MATCH` semi-join index-only. Also updated: `validateInvariants` (NO_EDR branch whose early `return` exempts it from the ADMIN/VULN gate on ALL_VULNS — a normal user must be able to file one, and it is safe because nothing is suppressed), `calculateAffectedCount` → 0, materialization skipped for NO_EDR, `kind` added to the `hasMatchingException`/`deleteExceptionForRequest` identity tuple and the import/export fingerprint (a NO_EDR and a legacy `ALL_VULNS × ASSET` row are otherwise indistinguishable — cancelling one would delete the other), a dedicated `(kind, asset)` duplicate check and supersede branch (the CVE-keyed ones early-return for NO_EDR), and `describeSubject` → "No EDR possible" (unfixed, approval mails read "All Vulnerabilities on host-x"). Entry point: a per-asset **No EDR** action in `AssetManagement.tsx`, shown only when `cloudInstanceId` is set, opening the new `NoEdrExceptionRequestModal` (fixed sentence, no subject/scope pickers); `POST /api/vulnerability-exception-requests` gates `kind=NO_EDR` on `assetFilterService.canAccessAsset`. Tests: `EdrCoverageKpiServiceTest`, `EdrCoverageKpiCountIntegrationTest`, `VulnerabilityExceptionRequestServiceNoEdrTest`, NO_EDR fixtures added to **both** agreement tests (`ExceptionMatchIndexTest`, `ExceptedFlagSqlAgreementIntegrationTest` — which only detect predicate drift if their fixtures contain a NO_EDR row) plus a V247 migration regression asserting a NULL-kind row still suppresses. - **CLI `manage-user-mappings import --start-risk-assessment`** — the mapping import (also `import-s3`) can auto-start a risk assessment for the owner of every **brand-new AWS account** it introduces. - **OS + CVE vulnerability exceptions (apply to all assets)** — new exception **scope `OS`** added to the two-axis model (Feature 196). Combined with subject `CVE` it means "these CVEs are excepted on every asset whose `Asset.osVersion` contains the OS string (case-insensitive substring)", e.g. exception OS `Windows Server 2019` also matches `Windows Server 2019 Datacenter`. The OS string is stored in the existing `vulnerability_exception.scope_value` column — **no DB migration** (`scope` is already `VARCHAR(20)`). The match predicate lives in three synchronized places, all updated: the entity `VulnerabilityException.scopeMatches()`, the native-SQL `ExceptionMatchSql.EXCEPTION_MATCH` (`LOCATE(LOWER(scope_value), LOWER(a.os_version)) > 0`, fanning out to ~36 query sites), and the in-memory `ExceptionMatchIndex` in `VulnerabilityService` (which now projects `a.os_version` into `StatusFilteredVulnerabilityRow`).
