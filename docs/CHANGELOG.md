# Changelog (archived from CLAUDE.md)

The full history. Every change is written here **verbatim** when it happens; CLAUDE.md's `## Recent Changes` carries a 2–3 line summary of the three newest and nothing more. Nothing is ever summarized on the way in — this file is the greppable detail. Newest first.

- **Generic chat notifications (Slack + Telegram), configurable per user** — SecMan can now message a user in Slack and/or Telegram when a reportable event completes, with each user choosing their own destination and, independently per channel, which events they want. Two events ship: `CROWDSTRIKE_REPORT_COMPLETED` ("New CrowdStrike report completed") and `AWS_ACCOUNT_IMPORT_COMPLETED` ("New AWS account import completed"). **Architecture is transport- and event-agnostic on purpose.** Publishers know nothing about chat: they publish a `ChatNotificationEvent` (event type, title, summary, label/value fields) and `ChatNotificationEventListener` (`@EventListener @Async`) hands it to `ChatNotificationService`, which resolves subscribers, destinations and rendering. Adding a reportable event is a `NotificationEventType` constant plus one publish call — the settings APIs, both settings UIs and the dispatcher all derive from the enum, so nothing else changes. Adding a transport is one client plus one branch, with no publisher touched. **Subscriptions are rows, not columns**: `user_notification_subscription (user_id, channel, event_type)` — so a new event type or a whole new channel costs no migration, "who wants X over Slack" is a single indexed lookup on the dispatch path, and one user can route CrowdStrike to Slack and AWS imports to Telegram. Saving one channel's settings never disturbs the other's subscriptions (the replace is a per-channel diff, which also preserves `created_at` on kept rows). **Destination resolution.** Slack: personal incoming webhook → the user's channel via the workspace bot → the workspace default channel. Telegram: the user's chat ID is always required (Telegram addresses a conversation, not a person), with the token being the user's personal bot if set, otherwise the workspace bot — so a personal bot keeps working even when workspace delivery is switched off. A subscriber who is enabled but has nowhere to send is recorded as `SKIPPED`, not `FAILED`; the UI resolves the same precedence client-side (`resolveSlackDestination` / `resolveTelegramDestination`) and warns *before* save rather than letting someone tick boxes that silently deliver nothing. **Where the events fire.** AWS account imports complete in one call, so `UserMappingBulkImportService.execute` (REST bulk + MCP, tagged with the calling entry point) and both `ImportController` upload paths publish immediately, after the import has committed and last among the post-commit side effects. CrowdStrike has no such point: a full CLI import arrives as ~94 sub-batch requests across 3 concurrent workers with no well-defined last batch, so `ImportCompletionNotifier` accumulates the run's totals in memory and a `@Scheduled` sweep publishes exactly **one** event once `SECMAN_CHAT_CROWDSTRIKE_QUIET_PERIOD_SECONDS` (180s) have passed with no activity — the same server-side debounce shape, and for the same reason, as `MaterializedViewRefreshService.requestDeferredRefresh`, and it keeps working for older CLI versions, the `/api/crowdstrike/vulnerabilities/save` path and manual callers. **Security.** The per-user Slack webhook URL is the only place in the platform where a non-admin supplies a URL the backend then fetches, so it is checked against a fixed `https://hooks.slack.com/` prefix *and* parsed-host equality (a prefix match alone passes `https://hooks.slack.com.evil.example/...`), rejects userinfo, non-default ports and non-https, and redirects are never followed. The Telegram bot token is interpolated into the request URL **path** (`/bot<token>/sendMessage`), so its `<digits>:<secret>` shape is validated as a security control — a token containing `/` or `..` would otherwise redirect the request to another path on the API host. Slack channels and Telegram chat IDs are validated against conservative character classes. Every credential (both workspace bot tokens, each user's webhook URL and personal bot token) is stored through `EncryptedStringConverter`, never returned by any API — the responses report only `…Configured: true/false` — and the `***HIDDEN***` mask is accepted back to mean "keep the stored value", with `''` meaning "clear it". Slack messages escape Slack's three reserved characters so an imported hostname cannot inject a fake link; Telegram messages are sent with **no** `parse_mode`, deliberately, because MarkdownV2 reserves 18 characters and rejects the whole message on one unescaped occurrence. Every route acts on the caller's own settings — the user id comes from the token and is never read from the body. Dispatch is deliberately **not** `@Transactional`: it performs outbound HTTP with a multi-second timeout per recipient, and wrapping it would pin a pooled DB connection for the whole fan-out (the 2026-07-21 HikariCP starvation incident was exactly that shape). Delivery is per-recipient and per-channel isolated: one bad webhook never stops another user's message, one channel's outage never suppresses the other, and nothing can propagate back into the import that published the event. **New endpoints**: `GET /api/notification-events` (catalogue, authenticated); `GET/PUT /api/slack/settings`, `POST /api/slack/settings/test`, `GET/PUT /api/telegram/settings`, `POST /api/telegram/settings/test` (authenticated, self-scoped); `GET/PUT /api/slack/config`, `POST /api/slack/config/test`, `GET/PUT /api/telegram/config` (ADMIN). No Telegram workspace test endpoint — a bot token addresses no conversation on its own, so a meaningful test needs a chat ID and lives on the user page. **UI**: `/chat-notifications` (all users, linked from the account dropdown) with independent Slack and Telegram cards sharing a `NotificationEventSelector` and `ChatDeliveryStatusLine`; `/admin/chat-config` (ADMIN, linked under System Configuration). **Schema**: `V251__chat_notifications.sql` adds `slack_config`, `telegram_config`, `user_slack_settings`, `user_telegram_settings`, `user_notification_subscription`. **Tests**: `SlackClientTest` and `TelegramClientTest` (the URL/token/channel/chat-id allowlists, including that a rejected value never reaches the network), `ChatMessageRendererTest` (both flavours + Slack escaping), `ChatNotificationServiceTest` (24 cases: subscription filtering, both destination precedence chains, skipped-vs-failed, per-recipient and per-channel isolation, outcome recording), `ImportCompletionNotifierTest` (94 sub-batches → one event with correct totals, nothing published mid-import, totals reset between runs, the account-ID list cap), and `chatValidation.test.ts` on the frontend (17 cases mirroring the backend validators and both destination resolvers). **Not verified in this environment**: `./gradlew build` and `./scripts/startbackenddev.sh` could not run — the session's egress policy blocks `services.gradle.org` and `repo1.maven.org`, and no Gradle 9.7.0 distribution or dependency cache is present — so the backend is compile-unverified and CLAUDE.md principle 5 and the principle-7 E2E gates are undischarged. - **MCP `get_vulnerabilities` no longer reads the whole vulnerability table** *(pre-existing OOM fix, unrelated to the EDR KPI change it shipped alongside)* — the no-filter branch for delegated (non-ADMIN) callers built its page by calling `vulnerabilityRepository.findAll()` and filtering/slicing in Kotlin, so every request loaded ~1.1M entities into heap and exhausted the 1 GB dev heap with an `OutOfMemoryError`; the cost scaled with the table rather than the requested page size.   Boxes that legitimately cannot run an agent are handled by a **third, orthogonal exception axis** `kind: ExceptionKind { VULNERABILITY, NO_EDR }` (V247) on both `VulnerabilityException` and `VulnerabilityExceptionRequest` — a *new enum*, not a new `Subject`/`Scope` value, so none of the ~15 exhaustive `when(subject)`/`when(scope)` blocks break and suppression semantics are not inherited. A NO_EDR exception is `scope=ASSET` only, stored with the filler `subject=ALL_VULNS`, **suppresses nothing**, and merely leaves the KPI denominator (reported separately as `excludedByNoEdrException` in the card subtitle). It reuses the entire request → approve/reject/cancel workflow, audit log, SSE badge and expiry scheduler. The "suppresses nothing" invariant is enforced in all three synchronized predicates — `VulnerabilityException.matches()`, `ExceptionMatchSql.EXCEPTION_MATCH` (one leading conjunct, compile-time interpolated into every native site incl. the `recomputeExcepted*` UPDATEs) and `ExceptionMatchIndex` — plus a defence-in-depth filter in `VulnerabilityService.getActiveExceptions()`. **The SQL guard is `(e.kind IS NULL OR e.kind = 'VULNERABILITY')`, not plain equality**: V247 adds the column `NOT NULL DEFAULT` with an explicit backfill, but if a NULL ever occurred (Hibernate `hbm2ddl.auto` creating it where V247 didn't apply, a restored pre-V247 dump) plain equality would stop *every* legacy exception matching and the 03:00 `recomputeAllExceptedScheduled` would clear `excepted` fleet-wide, unattended. The KPI queries use the opposite convention — plain `kind = 'NO_EDR'` — because tolerating NULL there would silently read every legacy exception as an EDR exemption. V247 also **rebuilds `idx_vuln_exception_covering` with `kind` leading**, since V203 created it specifically to keep the correlated `EXCEPTION_MATCH` semi-join index-only. Also updated: `validateInvariants` (NO_EDR branch whose early `return` exempts it from the ADMIN/VULN gate on ALL_VULNS — a normal user must be able to file one, and it is safe because nothing is suppressed), `calculateAffectedCount` → 0, materialization skipped for NO_EDR, `kind` added to the `hasMatchingException`/`deleteExceptionForRequest` identity tuple and the import/export fingerprint (a NO_EDR and a legacy `ALL_VULNS × ASSET` row are otherwise indistinguishable — cancelling one would delete the other), a dedicated `(kind, asset)` duplicate check and supersede branch (the CVE-keyed ones early-return for NO_EDR), and `describeSubject` → "No EDR possible" (unfixed, approval mails read "All Vulnerabilities on host-x"). Entry point: a per-asset **No EDR** action in `AssetManagement.tsx`, shown only when `cloudInstanceId` is set, opening the new `NoEdrExceptionRequestModal` (fixed sentence, no subject/scope pickers); `POST /api/vulnerability-exception-requests` gates `kind=NO_EDR` on `assetFilterService.canAccessAsset`.
